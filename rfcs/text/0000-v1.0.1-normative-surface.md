# RFC 0000 — Repair the v1.0.1 normative surface

## Summary

Two defects in the v1.0.1 Official Specification make parts of its own normative content
unimplementable, and both need normative correction rather than editorial repair.

First, the machine-readable schemas still carry the pre-v1.0.0 *Compiled Commitment* namespace
(`cc.*`) while the prose carries *Execution Change Contract* (`ecc.*`), and the fields that
Appendix Q's reference negative tests assert on are missing from both the §4.4.1/§4.7.1 field
tables and the schema files. `NT-007` is not expressible against the specification as published.

Second, Part III was replaced wholesale: the nine-phase development cycle went from 118 KB to a
4 KB chapter pair, and its content was amputated rather than migrated. Twenty-five
cross-references from Parts I, II, IV, V, VI and the appendices point into sections that no
longer exist. This RFC proposes writing the sections those references need, in the
Policy-as-Code idiom rather than restoring the nine-phase model.

## Motivation

Both problems were found while attempting to implement Appendix Q in the Minimal Reference
Harness. They are not stylistic.

**The schemas cannot express the conformance tests.** §4.8 requires `C6` to reject an ECC whose
`ecc.auth_ref` names an already-redeemed authorization, recording
`event.block_reason = AUTHORIZATION_ALREADY_REDEEMED`. NT-007 asserts on exactly that. But
`AUTHORIZATION_ALREADY_REDEEMED` is absent from the closed `event.block_reason` enumeration in
§4.7.1, and `ecc.auth_ref`, `ecc.exception_scope`, `ecc.decision_basis` and `event.auth_id` are
absent from the §4.4.1 and §4.7.1 field tables while being required by §4.3.1, §4.8 and NT-007.
An implementer following the tables alone builds a system that cannot pass the reference test the
same document defines.

**The event model is incomplete against its own Part VI.** Part VI criterion 2 accepts
`EXECUTION_COMPLETED`, `EXECUTION_FAILED` or `EFFECT_ATTESTED` as evidence of execution. §4.7.1
defines all three. `event.schema.json` declares none of them, and no example in Appendix Q
instantiates one.

**Twenty-five references resolve to nothing.** `Chapter 16` (change management, 5 references),
`§12.3 Step 5` (the invariant-architecture method, 9), `§11` and `§11.3` (deployment-model
selection and operational parameters, 4), `§13` / `§13.3` (threat assessment, 3), `§9.3 Step 4`,
`§10.6`, and `§7.4` — the last named by Appendix A, Appendix M and Framework structure as the
normative home of the Governance Architect role. Several sit inside MUST sentences: Part IV §18.2
requires a deployment model to be selected "during Phase C … (Part III, §11)", naming both an
abrogated phase and a section that does not exist.

A companion editorial pull request repairs what is repairable without changing meaning — three
corrupted Creative Commons licence declarations, five welded substitutions, seven surviving phase
names, a duplicated `event.chain_hash` table row, and an orphan stub block duplicated at the end
of two Parts. That work is deliberately separated from this RFC. Repairing damage restores what
v1.0.1 meant to say. Writing the sections its references should have pointed at does not, and is
what this RFC is for.

## Change level and impact

**normative-correction**, and one part of it is arguably **extension**: §7.3, §7.4 and Chapters
9–11 of Part III are new requirements, not corrections of existing ones. The higher
classification is claimed for the whole.

### What changes

| Surface | Change |
|---|---|
| `gar.schema.json`, `gga.schema.json` | Vocabulary alignment only; no field added or removed |
| `cc.schema.json` → `ecc.schema.json` | Renamed; `cc.*` → `ecc.*` throughout |
| `event.schema.json` | `CC_*` → `ECC_*`; `event.cc_id` → `event.ecc_id`; `event.emitter_signature` → `event.signature`; three effect-attestation types and the full signature block added |
| Part II §4.4.1, §4.7.1 field tables | Fields required elsewhere but absent from the tables are added to the tables (see below) |
| Part III | §7.3, §7.4 and Chapters 9–11 added |
| Parts I, II, IV, V, VI, Appendix H | 24 cross-references retargeted at the new sections |

### Backward compatibility

Breaking for any implementation that emitted `cc.*` records. The break is unavoidable: the prose
of v1.0.1 already says `ecc.*`, so an implementation following the schemas and an implementation
following the prose currently disagree, and one of them has to move. The specification's own text
is authoritative (Appendix B, "the prose schemas in Part II are authoritative; the JSON Schemas
are companion artifacts"), so the schemas move.

**Migration path.** A reader of a v1.0.0 `C5` log should treat `cc.*`, `CC_*`, `event.cc_id` and
`event.emitter_signature` as aliases of their `ecc.*` equivalents. No re-signing is required:
renaming a field would break the hash chain, so historical records stay as written and are read
through the alias table. `schemas/README.md` carries that table.

### Conformance impact

`NT-005`, `NT-006`, `NT-007` and `NT-008` become expressible and executable. A deployment that
claims L4 on the strength of NT-007 today is claiming it against a test that cannot be written as
specified.

## Detailed design

### 1. Fields required elsewhere but missing from the field tables

These are added to the §4.4.1 and §4.7.1 tables and to the schemas. Each is already imposed by a
normative section; the tables are what is defective.

| Field / value | Required by | Currently in the table? |
|---|---|---|
| `ecc.auth_ref` | §4.3.1, §4.8 | No |
| `ecc.exception_scope` | §4.3.1, §4.8 | No |
| `ecc.decision_basis` | Appendix Q NT-007 | No |
| `event.auth_id` | Appendix Q NT-007, Part VI §29.3 | No |
| `event.block_reason` value `AUTHORIZATION_ALREADY_REDEEMED` | §4.8 | No — the §4.7.1 enumeration is closed and lists five values |

`ecc.auth_ref` and `ecc.exception_scope` MUST be present if and only if `ecc.decision_basis` is
`PERMIT_WITH_AUTHORIZATION`, and absent otherwise.

### 2. Fields that are NOT adopted

`ecc.integrity_mode`, `ecc.decision_digest`, `event.decision_digest` and the error code
`ECC_DECISION_BINDING_INVALID` appear in v1.0.1 only as four bare sentences —

> `ecc.decision_digest` is used for bindings.
> `ecc.integrity_mode` defines ASYMMETRIC_SIGNATURE, HMAC, and REGISTRY_BOUND.
> `ECC_DECISION_BINDING_INVALID` is an error code.

— duplicated verbatim at the end of Part II and again at the end of Part III, outside any field
table, with no type, no MUST, and no rule saying what a binding is or when it fails. This RFC
proposes ruling them editorial residue and removing the two duplicated blocks. If the decision
binding is intended, it deserves its own RFC with an actual specification; adopting four
sentences as a normative mechanism would be worse than leaving it out.

### 3. Part III §7.3, §7.4 and Chapters 9–11

Written in the Policy-as-Code idiom, not as a restoration of the nine-phase cycle. The
correspondence to the dangling references:

| Dangling target | New section | What it specifies |
|---|---|---|
| `§7.4` (Governance Architect) | §7.4 Governance Roles | Governance Architect, Policy Authority Representative, Compliance Lead, Operations, and their incompatibilities |
| — | §7.3 Separation of Duties | The pipeline does not issue policy; proposal and approval are distinct principals for a `BLOCKING` invariant; Operations cannot alter `C5` |
| `§12.3 Step 5` (×9) | §9.3 Step 5 | Action-surface sizing; narrowing the surface as the lever that moves hazards out of the `E3` region |
| `§9.3 Step 4` | §9.2 Step 4 | Documented architectural exclusions |
| `§10.6` | §9.4 | Authorization propagation |
| `§13`, `§13.3` (×3) | §10.1, §10.2 | Threat assessment as a pipeline artifact; TH-1 assessed whatever severity it is given |
| `Chapter 16` (×5) | §11.1 | The governed change event |
| `§11` (×2) | §11.2 | Deployment-model selection and migration |
| `§11.3 Step 1`, `Step 4` (×2) | §11.3 | Unchanged — Chapter 11 is written to land on those numbers |

Chapter 10 additionally makes `NT-001`–`NT-008` a merge gate: the Validation step MUST execute
the applicable reference negative tests and MUST fail the change request on any failure. A
negative test MUST assert on the `C5` record rather than only on the refusal, and MUST NOT be
disabled to unblock a merge.

Chapter 11 §11.5 specifies `E3` analyzer versioning: a pinned analyzer version MUST NOT change in
place, every `E3`-involving decision MUST record `event.analyzer_version`, and an analyzer change
MUST trigger re-execution of the dependent negative tests. Without this, two decisions on
identical inputs that differ because the analyzer changed are indistinguishable from a
determinism failure, and I2 is unverifiable across time.

### 4. Validation gate

`spec/schemas/validate.py`, wired into CI, refuses a retired identifier, a re-declared editorial
residue, an out-of-namespace property, and any drop below the normative floor. This closes the
"CI does not validate the JSON schemas, nor any artifact against them" gap recorded as open in
`GOVERNANCE-DEVIATIONS.md`.

## Alternatives considered

**Do nothing.** The schemas stay contradicted by the prose, four reference negative tests stay
unimplementable, and twenty-five references stay dangling. Rejected: a conformance model whose own
tests cannot be written is not a conformance model.

**Retarget the dangling references at §7.2 and stop there.** Cheapest, and it was tried first.
Rejected: §7.2 is five bullet points about pull requests. Pointing "the threat assessment method"
at it produces a reference that resolves to text which does not contain what it promises — worse
than one that visibly dangles, because the failure is no longer detectable by a link checker.

**Restore the 118 KB nine-phase Part III.** Rejected: Part III §7.1 puts phase-gated methodology
"strictly outside the scope of the CROA execution path", and the project chose that direction
deliberately. The references need targets, not the old model back.

**Rewrite the referring sentences so they promise nothing.** Rejected for the normative ones:
Part IV §18.2's requirement to select and document a deployment model is a real obligation, and
deleting its cross-reference would leave the obligation without a method.

**Adopt `ecc.integrity_mode` and `ecc.decision_digest` as written.** Rejected: see §2. Four bare
sentences are not a specification, and adopting them would put an unspecified mechanism into a
normative schema.

## Risks and drawbacks

**This is a large normative change presented as a repair.** Chapters 9–11 are roughly 30 KB of new
requirements. Calling that a correction because it closes dangling references is a stretch, and a
reviewer is entitled to push back on scope. The alternative — leaving the references dangling
until each section is separately RFC'd — is defensible and slower.

**Breaking rename.** Any existing `cc.*` implementation breaks. The alias table mitigates reading
old records; it does not mitigate code.

**The new chapters are unproven.** They have not been through a pilot. Chapter 10's merge-gate
requirement in particular imposes real cost on a deployment: running the negative tests on every
change request is not free, and a project that cannot afford it will either skip the gate or
weaken the tests. Both failure modes are worse than an honest declaration that the gate is not
implemented.

**Authorship.** These sections were drafted in a single pass rather than accumulated from
practice. That is the opposite of how the rest of the framework was built, and it shows in the
absence of worked examples for Chapters 10 and 11.

## Open questions

1. **Scope.** Should Chapters 9–11 be split into three RFCs, reviewed independently? They serve
   different references and could land separately.
2. **`event.decision_basis` semantics.** NT-005 requires `AMBIGUOUS` on a `DENY` event, so the
   field records the *basis* rather than mirroring `event.type`. Q.1.2 and NT-006 use `DENY` on a
   `DENY`, mirroring the type. The two usages coexist without a rule reconciling them.
3. **`exit_status`, `failure_reason`, `attestation_reference`.** §4.7.1 names these without the
   `event.` prefix, unlike every other field. Editorial slip, or deliberate?
4. **Scope profile field names.** Appendix L §L.3 writes `scope.action_classes`;
   `event.schema.json` declares `action_classes` unprefixed inside the `scope` object, with
   `additionalProperties: false`. The two are incompatible as written.
5. **`cc-` prefixed values.** The Evidence Pack examples Q.1.1, Q.1.4 and Q.1.5 carry
   `"event.ecc_id": "cc-3e8f7a21-…"`. The field was renamed; the value kept the old prefix.
   Editorial, but worth fixing in the same pass.

## Prior art

The alias-table migration path follows the approach OpenTelemetry used for its semantic-convention
renames: old names remain readable, new names are canonical, and the mapping is published rather
than assumed. The separation between a repair pull request and a normative RFC follows the Rust
RFC convention that a "bug fix to the reference" and a "change to the language" travel by different
routes even when they touch the same file.
